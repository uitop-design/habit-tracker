# Habit Tracker

A small full-stack habit tracker: habits on a weekly schedule, daily check-ins, streaks and a
GitHub-style yearly heatmap. Single user, no authentication.

- **Today** — the habits scheduled for today with a progress bar, one-click check-ins and the
  current streak of every habit. Habits that are not scheduled today stay one click away.
- **Habit page** — current and best streak, total check-ins, 30-day completion rate and a yearly
  heatmap where any day of the last year can be checked in or out.
- **Archive** — archived habits keep their history and can be restored.

## Data model

**Habit** — `id` (uuid), `name` (1–48 chars), `color` (`slate`, `red`, `orange`, `amber`, `green`,
`teal`, `blue`, `violet`, `pink`), `weekdays` (`smallint[]`, ISO weekdays 1 = Monday … 7 = Sunday,
unique and sorted; all seven means every day), `archivedAt`, `createdAt`, `updatedAt`.

**Check-in** — `(habitId, date)` composite primary key, `createdAt`. Deleting a habit cascades to
its check-ins.

Names are unique among active habits, case-insensitively, enforced by a partial unique index on
`lower(name) WHERE archived_at IS NULL`.

## Streak rules

Streaks are computed by pure functions in `apps/api/src/domain/streaks.ts` from the list of
check-in dates and the habit's weekdays.

- Only **scheduled** days count. A check-in on an unscheduled day is stored and shown, but it
  neither extends nor breaks a streak.
- **Current streak** — consecutive scheduled days with a check-in, ending today. If today is
  scheduled but not checked in yet, the streak still counts up to the previous scheduled day:
  the day is not over.
- **Best streak** — the longest such run in the whole history.
- **30-day completion rate** — checked-in scheduled days divided by scheduled days over the last
  30 days including today, rounded to two decimals. The window never starts before the habit was
  created (or its first check-in), so a new habit is not penalised for days before it existed.
- The current schedule is applied to the whole history.

### Why the date comes from the client

A "day" depends on the user's time zone, which the server does not know. Every endpoint that
needs "today" takes it as a `YYYY-MM-DD` parameter with the browser's local date (`date`, or
`today` on check-in endpoints, where the path already has a `date`). Check-ins are accepted from
`today − 365` to `today + 1` days; the extra day covers clients that are already in tomorrow.

## API

All routes are prefixed with `/api`. Interactive docs: <http://localhost:3801/docs>.

| Method   | Path                                | Description                                         |
| -------- | ----------------------------------- | --------------------------------------------------- |
| `POST`   | `/habits`                           | Create a habit → `201`                              |
| `GET`    | `/habits?date=&archived=false`      | Habits with `scheduledToday`, `doneToday`, streaks  |
| `GET`    | `/habits/:id?date=`                 | One habit with the same fields                      |
| `PATCH`  | `/habits/:id`                       | Update `name`, `color` and/or `weekdays`            |
| `POST`   | `/habits/:id/archive`               | Archive (idempotent)                                |
| `POST`   | `/habits/:id/unarchive`             | Restore, `409` if the name is taken (idempotent)    |
| `DELETE` | `/habits/:id`                       | Delete with all check-ins → `204`                   |
| `PUT`    | `/habits/:id/checkins/:date?today=` | Check in (idempotent) → `204`                       |
| `DELETE` | `/habits/:id/checkins/:date?today=` | Remove a check-in (idempotent) → `204`              |
| `GET`    | `/habits/:id/stats?year=&date=`     | Year's check-in dates, streaks, totals, 30-day rate |
| `GET`    | `/health`                           | Database connectivity                               |

Check-ins of an archived habit cannot be changed (`409`). Request bodies are strict: unknown
fields are rejected.

Every error has the same shape:

```json
{
  "statusCode": 400,
  "error": "Bad Request",
  "message": ["query.date: Expected a valid calendar date"],
  "path": "/api/habits?date=2026-02-30",
  "timestamp": "2026-11-16T10:00:00.000Z"
}
```

Validation errors list every problem as `field: message`. Unique violations map to `409`, invalid
input syntax to `400`, and unexpected errors to a `500` without details (they are logged).

## Running with Docker Compose

```bash
docker compose up -d --build
```

| Service    | URL                          |
| ---------- | ---------------------------- |
| Web        | <http://localhost:3800>      |
| API        | <http://localhost:3801/api>  |
| Swagger UI | <http://localhost:3801/docs> |
| PostgreSQL | `localhost:5441`             |

The one-off `migrate` service applies migrations and seeds five habits with about five months of
history (relative to the day it runs, one of them archived). The seed is idempotent. nginx serves
the web app, falls back to `index.html` for client routes and proxies `/api` to the API.

To start from a clean database: `docker compose down -v && docker compose up -d --build`.

## Running locally

Requires Node.js 22.12+ and a PostgreSQL database (for example `docker compose up -d postgres`).

```bash
npm install
cp apps/api/.env.example apps/api/.env
npm run db:migrate -w apps/api
npm run db:seed -w apps/api
npm run dev
```

The API listens on <http://localhost:3801>, the Vite dev server on <http://localhost:5173> and
proxies `/api` to the API.

After changing `apps/api/src/db/schema.ts`, generate a migration with
`npm run db:generate -w apps/api`.
